# Conditional skill routes

## Goal

The PreToolUse skill router (`.agents/hooks/skill_router.py`, shipped by the `engineering` plugin) must
force an agent to load the standards that genuinely govern a write — but not every standard a stack owns.
Today every skill listed on a matching route blocks the write, so a C++ header demands seven skills
(`cpp:style`, `cpp:domain-design`, `cpp:mixins`, `cpp:structure`, `msvc:toolchain`, `win32:overview`,
`win32:style`) even for a header of plain free functions. That bloats context and contradicts the
SessionStart guidance, which says to load `cpp:domain-design` only "when designing records", and so on.

Split the responsibility along the existing plugin boundary:

- **Base (this repo, tj-agents/core):** the generic mechanism — a route schema that distinguishes
  *required* skills (block the write until loaded) from *conditional* skills (named in the router's
  message with the condition under which they apply, never blocking), and the router enforcing only the
  required tier. Language-agnostic: a future Rust pack uses it with no router change.
- **Each stack pack (first tj-agents/cpp):** the policy — which of its skills are required baseline for a
  path and which are conditional, expressed through its route generator
  (`tj-agents/cpp/.agents/gen_skill_routes.py`), then regenerated into consuming repos.

## Requirements

1. **Schema.** Extend a route entry so each skill is either required or conditional. A conditional entry
   carries a short condition (`when`: e.g. "composing or changing mixins / CRTP behavior providers").
   Pick the concrete JSON shape (for example `skills` stays required and a new `conditional: [{skill,
   when}]` list is added) and document it where the route contract is documented (`skill-routes` skill).
2. **Backward compatibility.** An existing route file with only `skills` behaves exactly as today: every
   listed skill is required. No consumer breaks before it regenerates.
3. **Router.** Block only on unloaded required skills. When a write matches conditional skills, include
   them in the block/nag message (name, description, `when`) without blocking, and do not repeat that
   advisory on every write in a session. A write whose route has no required skills never blocks.
4. **Narrower required routes remain possible.** A pack can still make a skill required for a narrow
   path (e.g. `cpp:mixins` required for `**/message/**` in winwrap-style layouts) by a separate route.
5. **Tests.** Cover: legacy file unchanged; required-only block; conditional-only never blocks;
   mixed route blocks only on the required subset; advisory message content; malformed conditional entry
   handling consistent with the router's existing fail-open policy for unusable routes.
6. **cpp pack (tj-agents/cpp).** Update `gen_skill_routes.py` so C++ sources require `cpp:style` (plus
   the selected API's style skill, e.g. `win32:style`) and list `cpp:domain-design`, `cpp:mixins`,
   `cpp:structure` as conditional with accurate conditions; `msvc:toolchain` required only for build /
   toolchain files (CMake, presets, vcxproj) and conditional for sources; `win32:overview` conditional.
   Keep test-path and build-path routes' existing required skills unless a skill is clearly conditional.
   Update its route CLI tests. Depends on the core change being available to consumers; sequence the
   PRs accordingly and say so in each PR body.
