## Continuation design

Reuse `persistent-workflow` and its shipped scheduler entry point. A new helper in the existing engineering workflows resource supplies a stable goal owner before a PR exists, then consumes the existing delivery binding when present. Do not introduce another workflow orchestrator or modify existing plan schemas.

The owner record binds repository, absolute worktree, branch, canonical goal path, completion condition, exact authorized actions, host and explicit finite limits. PR/head identity remains in the existing delivery binding. Resume state records active/waiting/blocked/complete, next action, evidence fingerprint, launch count, failures, deadline and terminal reason. Owner identity survives a supported repair rebind; arbitrary head, branch, worktree or goal replacement gates continuation.

The scheduled command runs a cheap deterministic observer. Pending or unchanged evidence does not launch a model. A meaningful failure or ready transition runs one bounded L4 repair/continuation context using the shipped lane table, the canonical goal pointer and fresh binding. Every invocation has a timeout and logs its result. Limits default to six launches, three consecutive transport failures and a 24-hour deadline, with stricter recorded user limits taking precedence. No bypass-permission flags. Headless invocation is a fresh context, never a same-chat wake.

Serialize state changes and scheduled writers with an OS-held file lock. Foreground sessions reserve this owner explicitly, refresh activity before work, and release it when yielding to a wait. A fresh reservation excludes wakes; a stale reservation whose process still exists becomes an observable reconciliation gate, never indefinite PID-only waiting or an unsafe automatic takeover. An exited reservation can recover. All supported writer launches remain under the supervisor lock, including interrupted child recovery; never delete a lock file to steal ownership.

The task name derives from the stable owner and cleanup checks an exact registration receipt. `-WhatIf` changes nothing. Re-registration preserves budgets and progress. Missing host/scheduler prerequisites fail explicitly. Terminal cleanup preserves the goal, final result and logs and removes only the exact owned job. An agent must explicitly checkpoint waiting, complete or a genuine gate; unexplained successful process exit is bounded recovery, not proof of completion.

Activation belongs at acceptance of substantive authorized work expected to outlive the session, and at the first delayed decision if that need arises later. It requires the actual authority and supported scheduler capability; installation alone never activates a live job. Quick work stays inline. Source implementation, isolated process/scheduler acceptance, authenticated host acceptance, publication and installed adoption are reported separately.
